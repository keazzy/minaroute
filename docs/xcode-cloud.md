# Xcode Cloud → TestFlight: step by step

Getting the current UI in front of testers without EAS. The app is **already on
TestFlight** (built with EAS previously), so the App Store Connect record exists
and some steps in generic guides don't apply here.

Bundle ID: `com.minaroute.app` · Scheme: `minaroute` · Version: `1.0.0`

---

## Step 0 — The one decision to make first

**Commit `ios/` to the repo.** Right now `ios/` and `android/` are gitignored
(managed / CNG workflow) and generated by `expo prebuild`.

That's a problem for Xcode Cloud specifically: when you create a workflow, Xcode
Cloud looks in the *repository* for an Xcode project so it can list schemes to
build. With `ios/` gitignored there's nothing to find, and setup either fails or
becomes fragile — the post-clone script does generate the project, but you're
relying on Xcode Cloud resolving a scheme it couldn't see at setup time.

Committing `ios/` is the well-trodden path and makes everything below
predictable. The trade is that when native config in `app.json` changes (a new
plugin, a permission string, the `waze` scheme we just added) you must re-run
prebuild and commit the result — it stops being automatic.

```bash
npx expo prebuild --platform ios
```

Then remove `/ios` from `.gitignore` and commit the folder. `ios/Pods/` and
`ios/build/` should stay ignored.

The post-clone script handles both cases — it skips prebuild when `ios/` is
present — so if you'd rather keep the repo clean, try it without committing
first and fall back to this if workflow creation can't see the scheme.

*(Ask me and I'll do this step — it's a mechanical change.)*

## Step 1 — Find your last EAS build number

**Do not skip this.** App Store Connect rejects any upload whose build number
isn't higher than the last one for the same version. Xcode Cloud's
`CI_BUILD_NUMBER` starts at **1** for a new workflow, which will almost certainly
be lower than what EAS already uploaded — so the very first build gets rejected
at the upload step, after a full successful build.

1. App Store Connect → **Apps → Minaroute → TestFlight → iOS builds**
2. Note the highest build number shown for version `1.0.0` (or whatever version
   is present).
3. Remember it for Step 4 (`BUILD_NUMBER_OFFSET`).

If the existing builds are under an older version and you bump `app.json`'s
`version` to `1.0.1`, this stops mattering — a new version starts its build
numbering fresh. That's the simpler route if you're happy to bump the version.

---

## Step 2 — Push the branch

Xcode Cloud builds from the git remote, not your working copy.

```bash
git push -u origin feat/home-redesign
```

---

## Step 3 — Create the workflow in Xcode

1. Open `ios/minaroute.xcworkspace` in Xcode.
2. Menu: **Product → Xcode Cloud → Create Workflow**.
3. Select the **minaroute** app target, then **Next**.
4. Grant Xcode Cloud access to the GitHub repository when prompted. It needs the
   repo linked before it can clone.
5. On the workflow screen, click **Edit Workflow** and set:
   - **Name:** `TestFlight — Internal`
   - **Branch:** `feat/home-redesign` (switch to `main` after you merge)
   - **Start Condition:** *Manual* to begin with. Turn on Branch Changes once a
     build has succeeded — otherwise every push burns compute on a broken setup.
   - **Environment:** latest released Xcode, **Clean: off**.
   - **Action:** delete the default *Build* action and add **Archive**, with
     platform **iOS** and deployment prep **TestFlight (Internal Testing Only)**.
6. **Save**. Don't run it yet — set the variables first.

---

## Step 4 — Set environment variables on the workflow

`.env.local` is gitignored, so the runner has none of it. Anything read at bundle
time must be a workflow variable or it will be `undefined` in the build.

Xcode → Report navigator → right-click the workflow → **Edit Workflow** →
**Environment** → Environment Variables.

| Variable | Value | Secret |
|---|---|---|
| `BUILD_NUMBER_OFFSET` | Your highest existing build number from Step 1 | no |
| `EXPO_PUBLIC_MAPBOX_ACCESS_TOKEN` | The `pk.…` token from `.env.local` | **yes** |
| `EXPO_PUBLIC_GOOGLE_PLACES_API_KEY` | From `.env.local` | **yes** |

Leave `MAPBOX_DOWNLOADS_TOKEN` unset. The Mapbox pods resolve without
credentials on this project today; only add it (an `sk.` token) if `pod install`
starts failing with a 401 on MapboxMaps.

**Never** set `SUPABASE_SERVICE_KEY` as an `EXPO_PUBLIC_*` variable. That prefix
embeds the value in the client bundle where anyone can extract it, and the
service_role key bypasses RLS entirely.

Without `EXPO_PUBLIC_MAPBOX_ACCESS_TOKEN`, the detail pages show the
"Map preview needs…" fallback instead of a map. The build still succeeds, which
is why this is easy to miss.

---

## Step 5 — Run it

**Start Build** in Xcode, or App Store Connect → the app → Xcode Cloud.

First run takes 15–25 minutes: it installs Node and CocoaPods, runs `npm ci`,
then `pod install`, then archives.

Watch the **post-clone** log section first — that's where anything will fail.

---

## Step 6 — TestFlight

1. App Store Connect → **TestFlight**. The build appears as *Processing*, then
   *Ready to Test* (usually 5–15 min).
2. Add testers under **Internal Testing** (up to 100 people who are on your App
   Store Connect team). Internal builds skip Beta App Review, so they're
   available in minutes.
3. External testers need Beta App Review — slower, and not worth it for a UI
   review build.

---

## What to tell your testers

**All content is placeholder.** Home's three sections and both detail pages
render hardcoded sample data, not the real 1,000-place database. Without this
warning, testers will report the same Lagos mosque appearing on every card as a
bug. What's worth their feedback: layout, typography, the carousels, dark mode,
the detail page structure, and whether the sticky action bar sits right.

The event posters in this build are third-party promotional artwork included for
demo purposes only — see `assets/images/home/CREDITS.md` before distributing
beyond a small internal group.

## If a step fails

| Symptom | Cause | Fix |
|---|---|---|
| Workflow creation can't find a scheme | `ios/` not in the repo | Step 0 |
| `pod install`: `Unicode Normalization not appropriate for ASCII-8BIT` | No UTF-8 locale | The script exports `LANG`/`LC_ALL`; a new step that shells out needs them too |
| `node: command not found` | Runners ship no Node | The script installs it; check the post-clone log for the `brew install` line |
| Upload rejected: build number already used | `CI_BUILD_NUMBER` below the EAS history | Raise `BUILD_NUMBER_OFFSET` (Step 1/4) |
| 401 on MapboxMaps during `pod install` | SDK needs credentials | Add `MAPBOX_DOWNLOADS_TOKEN` (`sk.` token) as a secret variable |
| Maps show the fallback in TestFlight | `EXPO_PUBLIC_MAPBOX_ACCESS_TOKEN` unset | Step 4 |

The post-clone script is **untested in Xcode Cloud** — written against the
documented runner environment. The first run is the real test.
